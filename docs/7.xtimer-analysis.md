# XTimer 架构分析与 ChronoFlow 重构方案

## 一、三篇文章总结

### 1.1 workflow.timer — 基于 MQ 的分布式定时器

**来源：** [juejin.cn/post/7116320697139331103](https://juejin.cn/post/7116320697139331103)

**核心架构：** 3 个模块 + 2 道 MQ（Apache Pulsar）

```
Scheduler --[MQ]--> Trigger --[MQ]--> Executor
```

**模块职责：**

| 模块 | 职责 |
|------|------|
| Scheduler | 每轮推算分钟级时间范围，为每个二维分片抢分布式锁，抢到后生产令牌投递到 MQ |
| Trigger | 消费令牌，在时间片内持续轮询 Redis ZSet，取出到期任务投递到下游 MQ |
| Executor | 消费任务消息，幂等去重（bloom filter + MySQL），执行任务，更新记录 |

**核心设计思想：**

1. **主动轮询 + 有序表**：用 Redis ZSet（score = 执行时间戳）替代全量扫描，查询从 O(N) 优化到 O(logN)
2. **纵向分治（时间分片）**：按分钟级时间范围切分 ZSet，每个分片独立 key，减少单次查询量
3. **横向分治（分桶）**：每个时间片内按 `timer_id % bucket_num` 分桶，每个桶一个 goroutine 并发处理
4. **二维分片**：key = `{time_range}:{bucket}`，实现资源隔离和并发

**问题：**
- 串行打点：执行完一个任务才创建下一个，不支持高频（1s 级）定时器
- Redis 重度依赖：所有数据都在 Redis 中，可靠性风险
- 静态分桶：启动时配置，不可动态调整
- 依赖 Apache Pulsar MQ，接入成本高

### 1.2 xTimer — 基于协程池的分布式定时器

**来源：** [juejin.cn/post/7174007780104208392](https://juejin.cn/post/7174007780104208392)

**核心架构：** 3 个模块 + 2 个协程池（ants），仅依赖 MySQL + Redis

```
Scheduler --[goroutine pool]--> Trigger --[goroutine pool]--> Executor
```

**对 workflow.timer 的改进：**

| 改进项 | 说明 |
|--------|------|
| 去 MQ 化 | 用 ants 协程池替代 Apache Pulsar，降低接入成本 |
| 批量打点 | 激活定时器时批量预创建未来两个 step1 时间范围内的定时任务 |
| 三级存储 | MySQL → Redis → 节点内存，Migrator 模块负责迁移 |
| 动态分桶 | 根据任务数量动态计算分桶数 |

**模块详细流程：**

**Scheduler（每 1s 轮询）：**
1. 计算当前分钟级时间范围 `time_range`
2. 遍历桶号 0 ~ bucketNum-1
3. 对每个桶尝试 `SETNX` 抢锁，TTL < 时间片时长
4. 抢到锁 → 从协程池提交 Trigger 协程

**Trigger（被 Scheduler 启动）：**
1. 在时间片内持续轮询 Redis ZSet `{time_range}:{bucket}`
2. `ZRANGEBYSCORE` 取 score <= now 的到期任务
3. 从协程池提交 Executor 协程执行每个任务
4. 完成后更新锁 TTL（延长过期时间，标记分片已处理）

**Executor（被 Trigger 启动）：**
1. bloom filter 快速查重
2. 若命中，查 MySQL 确认
3. 查询定时器定义（先内存缓存，miss 再查 MySQL）
4. 执行 HTTP 回调
5. bloom filter 打点
6. 更新 MySQL 执行记录状态

**Migrator（一级迁移，每隔 step1 触发）：**
1. 全量扫描 MySQL 中 ACTIVE 的定时器定义
2. 解析下一个 step1 时间范围内的所有执行时间点
3. 批量插入 timer_records 到 MySQL
4. 按 `{time_range}:{bucket}` 分组批量 ZAdd 到 Redis

**Migrator（二级迁移，位于执行器模块，每隔 step2 触发）：**
1. 获取下一个 step2 内的定时任务列表
2. 提前将定时器完整定义缓存到节点内存

### 1.3 xTimer 压测结果

**来源：** [juejin.cn/post/7175433651327336504](https://juejin.cn/post/7175433651327336504)

| 场景 | 成功率 | P99 延时 |
|------|--------|----------|
| 1000 笔定时器同时执行 | 100% | 2.4s |
| 2000 笔定时器同时执行 | 100% | 9.1s |

**性能瓶颈分析：**
- 瓶颈不在调度逻辑，而在瞬时 Redis/MySQL 连接数激增
- 2G2 核云服务器资源有限，连接池成为瓶颈
- 逻辑层面无性能问题

## 二、三种方案对比

| 维度 | workflow.timer | xTimer | ChronoFlow（当前） |
|------|---------------|--------|-------------------|
| 模块通信 | Apache Pulsar MQ | ants 协程池 | 原生 chan + goroutine |
| 外部依赖 | MySQL + Redis + Pulsar | MySQL + Redis | MySQL + Redis |
| 时间分片 | 有（分钟级） | 有（分钟级） | 无（单一 ZSet） |
| 分桶并发 | 有（静态） | 有（动态） | 无 |
| 分布式锁位置 | Scheduler | Scheduler | Trigger |
| 任务预创建 | 串行打点 | 批量打点（Migrator） | 实时扫描 DB |
| 存储模型 | 二级（MySQL + Redis） | 三级（MySQL + Redis + 内存） | 二级（MySQL + Redis） |
| 幂等去重 | bloom filter + MySQL | bloom filter + MySQL | bloom filter + Redis key |
| 任务粒度 | Timer 定义 + Timer Task 分离 | Timer 定义 + Timer Task 分离 | Task 即定义即任务 |
| 接入成本 | 高（需 Pulsar） | 低 | 低 |

## 三、推荐方案：以 xTimer 为蓝本重构 ChronoFlow

### 3.1 选择 xTimer 的理由

1. **接入成本最低**：仅依赖 MySQL + Redis，无需 MQ 组件
2. **性能更优**：协程池内通信，减少 IO 交互，延时更低
3. **架构更成熟**：批量打点、三级存储、动态分桶均已实现
4. **100% 成功率验证**：压测证明方案可行

### 3.2 整体架构

```
┌─────────────────────────────────────────────────────┐
│                    ChronoFlow                        │
│                                                     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐      │
│  │ Migrator │    │Scheduler │    │  Trigger │      │
│  │(批量打点)│    │(抢锁+分发)│    │(轮询ZSet)│      │
│  └────┬─────┘    └────┬─────┘    └────┬─────┘      │
│       │               │               │             │
│       │          [goroutine pool]      │             │
│       │               │               │             │
│       ▼               ▼               ▼             │
│  ┌──────────────────────────────────────────┐       │
│  │              Executor                     │       │
│  │  (幂等去重 + HTTP回调 + 更新记录)          │       │
│  └──────────────────────────────────────────┘       │
│                                                     │
│  ┌──────────────────────────────────────────┐       │
│  │           内存缓存层 (Memory Cache)       │       │
│  │  (定时器定义缓存, TTL 过期, 读写锁)        │       │
│  └──────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────┘
         │                │                │
    ┌────▼────┐     ┌────▼────┐     ┌────▼────┐
    │  MySQL  │     │  Redis  │     │  Memory │
    │(持久化) │     │(ZSet队列)│     │(本地缓存)│
    └─────────┘     └─────────┘     └─────────┘
```

### 3.3 核心流程

```
定时器创建 → 定义存 MySQL（status=INACTIVE）
     │
定时器激活 → Migrator 批量预创建未来 2 个 step1 的定时任务
     │         → 定时任务存 MySQL + Redis ZSet（按分片分桶）
     │
每 1s → Scheduler 轮询
     │   → 计算当前 time_range
     │   → 遍历每个桶，抢分布式锁
     │   → 抢到锁 → 从协程池提交 Trigger
     │
Trigger → 在时间片内轮询 Redis ZSet {time_range}:{bucket}
     │    → ZRANGEBYSCORE 取到期任务
     │    → 从协程池提交 Executor
     │    → 完成后更新锁 TTL
     │
Executor → bloom filter 查重
     │    → MySQL 查重（bloom 命中时）
     │    → 查定时器定义（先内存，miss 再 MySQL）
     │    → 执行 HTTP 回调
     │    → bloom filter 打点
     │    → 更新 MySQL 记录状态
     │
Migrator（每隔 step1）→ 扫描 ACTIVE 定时器
     │                  → 批量创建下一个 step1 的定时任务
     │                  → 批量推入 Redis ZSet
```

### 3.4 数据模型变更

**新增 `timer_definitions` 表（定时器定义）：**

```sql
CREATE TABLE timer_definitions (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    app             VARCHAR(128) NOT NULL COMMENT '应用名',
    name            VARCHAR(128) NOT NULL COMMENT '定时器名称',
    cron_expr       VARCHAR(64)  NOT NULL COMMENT 'Cron表达式',
    callback_url    VARCHAR(512) NOT NULL COMMENT '回调URL',
    callback_method VARCHAR(16)  NOT NULL DEFAULT 'POST',
    callback_body   TEXT,
    callback_headers TEXT,
    status          VARCHAR(32) NOT NULL DEFAULT 'INACTIVE' COMMENT 'ACTIVE/INACTIVE/DELETED',
    timeout         INT DEFAULT 30,
    max_retries     INT DEFAULT 3,
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME NOT NULL ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_status(status),
    INDEX idx_app(app)
);
```

**新增 `timer_records` 表（定时任务记录）：**

```sql
CREATE TABLE timer_records (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    timer_id        BIGINT NOT NULL COMMENT '定时器ID',
    trigger_time    DATETIME NOT NULL COMMENT '执行时间',
    status          VARCHAR(32) NOT NULL DEFAULT 'PENDING',
    retry_count     INT DEFAULT 0,
    request_url     VARCHAR(512),
    request_method  VARCHAR(16),
    request_body    TEXT,
    response_code   INT,
    response_body   TEXT,
    error_message   TEXT,
    started_at      DATETIME,
    finished_at     DATETIME,
    duration        BIGINT COMMENT '毫秒',
    next_retry_time DATETIME,
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME NOT NULL ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_timer_id(timer_id),
    INDEX idx_trigger_time(trigger_time),
    INDEX idx_status(status),
    INDEX idx_next_retry_time(next_retry_time)
);
```

### 3.5 Redis Key 结构

| 用途 | Key 格式 | 类型 |
|------|----------|------|
| 任务队列 | `chronoflow:timer:{YYYY-MM-DD-HH:mm}:{bucket}` | ZSet (score=执行时间戳) |
| Scheduler 锁 | `chronoflow:scheduler_lock:{time_range}:{bucket}` | String (SETNX) |
| 幂等键 | `chronoflow:idempotent:{timer_id}:{trigger_time_ms}` | String (SETNX) |
| 布隆过滤器 | `chronoflow:bloom:{date}` | String (bitmap) |

### 3.6 配置变更

```yaml
scheduler:
  step1_duration: 3600    # 一级时间步（秒），默认 60 分钟
  step2_duration: 300     # 二级时间步（秒），默认 5 分钟
  bucket_num: 3           # 默认分桶数量（支持动态调整）

executor:
  timeout: 30
  max_retries: 3
  worker_pool_size: 100   # 协程池大小
```

## 四、可优化的点

### 4.1 布隆过滤器误判优化

**xtimer 问题：** bloom filter 误判时回查 MySQL，增加 DB 压力。

**优化方案：** 在 Executor 中增加 Redis 幂等键（SETNX）作为第二层快速去重，只有 Redis 也命中时才回查 MySQL。

```
bloom filter → miss → 执行
bloom filter → hit → Redis 幂等键检查
                    → miss → 执行（bloom 误判）
                    → hit  → MySQL 查重
                           → 已执行 → 跳过
                           → 未执行 → 执行
```

### 4.2 Migrator 批量写入优化

**xtimer 问题：** Migrator 全量扫描所有 ACTIVE 定时器，当定时器数量大时效率低。

**优化方案：**
1. 使用 Redis 缓存 ACTIVE 定时器 ID 列表，避免每次全量扫描
2. 批量写入 MySQL 时使用 `INSERT ... ON DUPLICATE KEY UPDATE` 避免重复插入
3. Redis ZAdd 使用 pipeline 批量写入

### 4.3 动态分桶策略优化

**xtimer 提出的方案：** 根据任务数量动态计算分桶数。

**优化方案：** 引入自适应分桶算法：

```go
func calculateBucketNum(taskCount int) int {
    if taskCount < 100 {
        return 1
    } else if taskCount < 1000 {
        return 3
    } else if taskCount < 5000 {
        return 5
    } else {
        return int(math.Ceil(float64(taskCount) / 1000))
    }
}
```

同时建立 `time_bucket_mapping` 表记录每个时间范围对应的分桶数。

### 4.4 内存缓存淘汰策略

**xtimer 问题：** 仅靠 TTL 过期，可能出现缓存污染（已 INACTIVE 的定时器仍在缓存中）。

**优化方案：**
1. 定时器状态变更时主动通知所有节点（通过 Redis Pub/Sub）
2. 使用 LRU 淘汰策略，限制缓存条目数量
3. 缓存命中率监控

### 4.5 Scheduler 锁竞争优化

**xtimer 问题：** 每个桶一把锁，bucket_num 大时锁竞争激烈。

**优化方案：**
1. 使用 Redis Hash 存储多个桶的锁状态，一次 pipeline 完成多桶抢锁
2. 引入锁续约机制，避免 Trigger 执行时间超过锁 TTL 导致锁提前释放

### 4.6 连接池优化（压测瓶颈）

**xtimer 压测发现：** 瓶颈在瞬时 Redis/MySQL 连接数激增。

**优化方案：**
1. Redis 连接池大小根据 bucket_num 和 worker_pool_size 计算
2. MySQL 连接池大小 = bucket_num * 2 + 余量
3. 使用连接池预热，避免冷启动时连接建立延迟
4. Redis pipeline 批量操作减少 RTT

### 4.7 定时器定义变更处理

**xtimer 方案：** 只允许激活/去激活，不允许修改定义。修改需删除重建。

**优化方案（更友好）：**
1. 允许修改，但修改后触发 Migrator 重新预创建
2. 对于已推入 Redis 的旧记录，采用"只打点不删点"原则
3. Executor 执行时检查定时器状态，INACTIVE 则跳过

### 4.8 监控增强

**在 xTimer 基础上增加：**
1. Prometheus 指标：调度延迟、触发成功率、执行耗时分布
2. 分片处理监控：每个分片的处理耗时、任务数量
3. 缓存命中率：内存缓存和 Redis 的命中/miss 统计
4. 告警：任务执行失败率超阈值、调度延迟超阈值

## 五、实施路线

| 阶段 | 内容 | 优先级 |
|------|------|--------|
| P0 | 数据模型（timer_definitions + timer_records） | 高 |
| P0 | Redis 分片分桶 + ants 协程池 | 高 |
| P0 | Scheduler 重构（分布式锁 + 协程池） | 高 |
| P0 | Trigger 重构（时间片轮询） | 高 |
| P0 | Executor 重构（幂等去重） | 高 |
| P1 | Migrator 模块（一级迁移） | 高 |
| P1 | 内存缓存层（二级迁移） | 中 |
| P2 | 动态分桶 | 中 |
| P3 | 监控增强 | 低 |
| P3 | 前端适配 | 低 |
